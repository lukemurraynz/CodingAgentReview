# Alert pairing

## Active alerts

| Alert name | Azure signal | Emitting call site | Why not orphaned |
| --- | --- | --- | --- |
| `alert-<namePrefix>-sb-deadletter` | Service Bus metric `DeadletteredMessages` filtered to `EntityName=review-requests` | `src/harness/queue.py:ReviewQueueConsumer.receive` abandons failed messages and the queue dead-letters after max delivery count | The metric is tied to the only declared queue (`review-requests`) and the consumer's abandon path is the code path that drives dead-letter accumulation. |
| `alert-<namePrefix>-sb-backlog` | Service Bus metric `ActiveMessages` filtered to `EntityName=review-requests` | `src/controlplane/__init__.py:_send_event` enqueues every accepted review event; `src/harness/queue.py:ReviewQueueConsumer.receive` drains that same queue | Backlog is generated by real producers and consumers in the harness, so the alert follows the actual review-request pipeline. |
| `alert-<namePrefix>-review-run-failures` | Application Insights `AppTraces` query over worker failure messages | `src/worker/runner.py:execute_review` logs `lens %s failed (%s): %s` and `annotation posting failed: %s`; `src/harness/telemetry.py:configure_telemetry` exports stdlib logs when `APPLICATIONINSIGHTS_CONNECTION_STRING` is present | The query matches the exact worker log messages that indicate degraded or failed review execution and only becomes active once telemetry export is configured by infra. |
| `alert-<namePrefix>-cosmos-429` | Cosmos DB metric `TotalRequests` filtered to `StatusCode=429` | `src/harness/repository.py:HarnessRepository.put_run`, `put_finding`, `get_findings`, and `query_runs_for_change` drive Cosmos traffic for `reviewRuns`, `findings`, and `episodes` reconstruction data | Those repository methods are the persisted review-state path, so 429s on the account are directly connected to the harness state store. |
